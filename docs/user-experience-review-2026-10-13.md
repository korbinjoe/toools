# Toools 用户视角的信息架构与 UI 评审

日期：2026-10-13。评审范围：当前工作区源码、当前本地 HTTP 响应，以及线上站点的 HTML 内容。没有修改网站代码或发布配置。

## 总体判断

产品已经建立了合理的两条路径：不知道用什么时按工作流探索，知道目标时直接找工具。当前主要问题在于发现之后的选择过程：页面展示大量名称、分类和热度，但预算、适用条件、推荐理由和工具间关系还不足以支撑快速决策。

建议保留工作流优先的定位，优先改善推荐准确性、统一工具浏览体验，再调整首页信息密度和移动端决策区。现有暖色、统一字体、圆角卡片和有限主色可以沿用；本次没有截图，不能据此评价实际视觉完成度。

## 证据与限制

- 本次直接 HTTP 读取确认线上 `/stacks/indie-developer-toolkit`、`/tools?q=notion`、`/categories`、`/tools/figma` 返回 200，并检查返回的文字和链接。
- 本地首页、Stacks 列表、Stack 详情、Submit 返回 200；本地 `/tools`、`/categories` 返回 500。线上和本地状态不同，不能把本地错误归因于线上。
- 线上工作流详情最新响应包含工具详情链接、阶段说明和编辑推荐说明。本地工作流详情进入了预览降级状态，工具不可点击且统一显示 Freemium。
- 浏览器截图取证未完成：当前环境没有可调用的内置 Browser 会话，Browser Use 未连接，Chrome 扩展离线；备用浏览器安装未完成，已停止。这是结构和实现层评审，不是已经完成的截图视觉审计。
- 未验证实际手机渲染、点击交互、键盘全流程、屏幕阅读器、真实用户行为、转化率或线上加载性能。
- Web 工具对工作流页面返回的缓存内容与本次直接 HTTP 最新响应不同。关于工作流可点击性及编辑说明，以本次最新 HTTP 响应为准。

## 用户路径与健康度

| 步骤 | 用户任务 | 判断 |
| --- | --- | --- |
| 1 | 首页理解网站并选择入口 | 定位基本清楚；Stacks 术语及重复入口增加理解成本，九个完整工作流预览使页面过长。 |
| 2 | 从 Stacks 列表选场景 | 角色和工作流分组有价值；仍缺预算、经验要求和明确产出等取舍信息。 |
| 3 | 阅读 Indie Developer Toolkit | 线上有完整阶段、编辑说明和详情链接；相同阶段混合替代与互补工具，没有明确默认方案。 |
| 4 | 查看 Figma 并判断是否采用 | 用途、优缺点、工作流回链有帮助；替代推荐准确性不足，手机布局将价格和行动区放到很后面。 |
| 5 | 搜索 Notion、缩小候选范围 | 线上返回 20 项；名称命中、替代产品、集成和版本条目混排，原始 Markdown 进入简介；交互未实测。 |
| 6 | 通过分类浏览工具 | 分类列表可访问；宽泛类别包含数百工具，分类详情实现没有筛选和分页，不能快速缩小范围。 |
| 7 | 提交工具 | 提交要求和外部 GitHub 入口清楚；没有 GitHub 账号的用户缺乏真实低门槛替代途径。 |

## 信息架构问题

### P1：推荐的功能匹配不足，损害信任

线上 Figma 详情的 Alternatives 包含 MarkText。MarkText 的页面描述为 Markdown 编辑器；用户寻找 UI 设计和交互原型工具时，这个候选不满足同一任务。

源码 `src/app/tools/[slug]/page.tsx` 的 `getAlternatives` 仅匹配相同大分类，再按 GitHub stars、Product Hunt votes 和浏览量排序。热度不能证明可替代性。

建议先限定相同核心用途，再呈现价格、协作、部署方式等差异；没有足够相关候选时减少推荐数量。可以先人工维护重点工具的替代关系，无需先实现复杂推荐系统。

影响范围：工具详情 Alternatives，以及工作流 Explore more 的候选相关性。保留已有页面路由。

### P1：同一找工具任务有两套不同体验

Browse 页面提供搜索、筛选和分页；分类详情单独查询全部工具，只展示工具网格。线上分类列表显示 Design 752 项、Development 964 项。如此规模需要子类和筛选支持，单一大分类无法帮助用户做选择。

建议让分类入口进入同一套带预选类别的浏览体验。路由可以保留，但搜索、筛选、结果计数、排序和分页使用统一结构。

影响范围：Browse、Categories 详情及两者的跳转；不需要重建分类首页。

### P1：工作流列出了组合，但没有明确最小方案

线上每个阶段都有编辑说明，这是优势；但同一阶段仍会同时出现多个工具，例如分析与监控阶段的 Mixpanel、PostHog、Sentry、Hotjar、Grafana。用户需要判断哪些互相替代、哪些需要组合，以及哪些可以稍后再引入。

建议每阶段先给一个默认推荐，再展示“什么时候换另一个”和“可选补充”；顶部给出最小可用组合、预算区间和适用前提。预算必须来自维护的数据，不能凭空估算。

影响范围：Stack 详情内容结构与推荐数据；工具库本身仍可保留。

### P1：首页承担过多详情展示

首页在 Popular Stacks 下直接渲染全部九个工作流，每个卡片展示完整阶段和工具链。用户还没选择场景，就必须扫描大量工具名称；Editor's Picks、Recently Added 和分类都在后面。

推荐首页只放三至四个代表场景。卡片优先显示目标、适用人群和一句推荐理由，完整工具链移到详情。导航主入口建议采用 Workflows 和 Tools，Categories 作为 Tools 内部的浏览维度；贡献入口降低到辅助导航。

首屏同时存在 Search Tools 按钮、搜索框及导航搜索图标。可让搜索框承担直接找工具的任务，让工作流按钮承担场景探索任务。面向英文用户的命名应保持英语，不需要仅因为本次评审使用中文就改为中文界面。

影响范围：首页、导航文案与卡片信息层级。

### P1：筛选维度与搜索结果未围绕决策组织

FilterPanel 在结果上方依次完整展示 Sort、Signals、Platform、Category、Pricing，排序与 Signals 占据最前位置。用户先要解决“做什么、多少钱、能否在我的设备上使用”，这些条件优先级更高。

Open Source 同时出现在 Signals 和 Pricing。开源和收费方式是独立属性，应拆开；平台筛选值 Mac 与线上 Figma 的 macOS 标记不一致，存在匹配遗漏风险，尚未通过交互验证。

搜索 Notion 返回 20 项，包括 Notion、Notion Calendar、Notion 3.4、Notion Developer Platform、替代工具和描述中提到 Notion 的产品。当前源码没有按文本相关性排序，用户必须自行区分本体、集成和替代品。

建议默认显示类别、价格和结果；排序压缩为单个控件，其余条件放入更多筛选。增加已选条件、清空条件和零结果恢复动作。搜索先按名称与任务相关性排序，再用热度作为补充，并对同一产品的版本条目进行归并或明确标识。

影响范围：Browse 搜索、筛选、空状态及工具数据规范。

## UI 与可访问性风险

### P1：手机端价格和主行动出现过晚

工具详情是主内容加右侧栏的网格。在小屏幕下变为单列；右侧栏在源码顺序上位于 About、Use Cases、Pros & Cons、工作流回链及 Alternatives 之后。因此 Visit Website、Pricing 和 Platforms 都需要先经过这些内容才能到达。

建议将名称、用途、价格、平台和主行动组成顶部决策区；较长说明保留在下面。必要时增加底部固定行动，但应先检查是否遮挡内容。本次未实际渲染手机页面，不能给出折数或滚动距离。

影响范围：工具详情响应式布局。

### P1：浅色主按钮的小字号文字对比度不足

当前浅色主题主色为 `#D97706`，主色文字为 `#FEFCE8`，根据 sRGB 相对亮度计算，对比度约 3.08:1。主按钮文字常用 13px 或 14px；这一组合低于普通文字常用的 4.5:1 目标。橙色文字对白色约 3.19:1，也应检查小字号链接。

建议为主按钮采用更深背景或更深文字，保持暖色品牌。灰色文字进一步叠加 50%／60% 透明度时也有风险，应按实际背景逐项测量。

影响范围：浅色主题按钮与文本颜色 token。这里是源码色值计算，不代表完整 WCAG 合规检查。

### P2：细节信息过小且卡片语义不一致

工具卡片标签采用 10px，部分工作流文字为 11px，编号为 7px；简介经常截断。最需要比较的信息容易在视觉上成为次要信息。首页工作流还使用字母方块代替工具真实图标，用户辨认成本较高。

工具列表卡片使用右上箭头，实际点击进入站内详情；Submit 的同类箭头则代表站外。建议站内详情使用清楚的 View details 提示，出站行动统一使用外链符号。

源码里搜索框缺少明确的 label／aria-label、导航搜索图标按钮没有可访问名称、筛选按钮没有 aria-pressed。部分 Link 包裹 Button 还需检查实际渲染后的交互语义和键盘行为。

影响范围：共享卡片、搜索框、导航和筛选组件。实际触控尺寸、文字截断效果及键盘焦点仍需浏览器验证。

## 内容质量与信任

- 最新线上响应的工具简介出现 `[![Open-Source Software]...]`、`![Freeware]...` 等原始 Markdown。这不是用户需要看到的产品介绍，应在导入阶段提取干净摘要、过滤标记和源站说明。
- Popular Stacks 来自固定预览数据，不是受欢迎程度的排名。若没有真实统计支持，建议改成 Featured Workflows 或 Curated Workflows。
- 首页预览和数据库中的工作流详情使用不同数据源。Indie Developer 的首页展示与最新线上详情的工具组合不同，应统一数据，避免用户点击后发现推荐内容变化。
- 工具详情缺少具体价格、免费版限制及价格核验日期。对要采用工具的用户，这比站内浏览和点击次数更重要。
- 缺少 GitHub 地址或 star 数不能直接证明 Closed source。当前详情实现把这种缺失显示为 Closed source，应以明确的开源状态或 Unknown 区分。
- Submit 声称无 GitHub 账号可通过现有 issue 邮件联系，但没有邮件地址或真实邮件入口。若继续面向创作者和运营用户，应提供可用的联系渠道。

## 本地可用性问题，单独记录

本地 Browse 和 Categories 返回 500；首页数据库查询失败时直接隐藏工具和分类区块，而 Stacks 降级为预览。预览统一标注 Freemium 且工具不可点击，没有告知用户当前数据不可用。

这会让技术故障表现为“网站内容少、卡片不能点击”。应显示可理解的失败状态和重试入口；未知价格显示 Unknown，不应生成默认价格。本次线上最新工作流响应是完整数据，不应把本地的降级状态描述为线上常态。

## 推荐改造顺序

1. 清洗简介，校正替代推荐、价格及开源语义，统一首页和详情的数据来源。先提高信息可信度。
2. 统一分类与工具浏览，精简筛选，补充相关性排序及清空条件。让用户更快缩小候选范围。
3. 工作流补充默认方案与取舍说明，首页缩减预览，工具详情把决策区前置。让用户更快作出决定。
4. 调整对比度、字号、控件名称和焦点语义，再进行桌面与手机截图、键盘全流程验证。

首轮建议覆盖首页、Browse／分类详情、Stack 详情、Tool 详情及共享组件；这是页面组织、内容质量和推荐规则的调整，不需要先做全站视觉重建。

可用于后续验证的用户任务：新用户能否快速说清网站用途并找到场景；能否在少量候选中解释为何选择一个工具；能否在手机上快速找到价格和访问入口。验收指标应在真实任务测试后确定，本次不宣称转化提升。
